# 售票平台 AI 客服与运营问数中台架构

`damai-ai` 的设计主线收束为“客服入口 → 意图识别 → 知识/业务工具回答 → 人工升级 → 反馈评测闭环”。项目不再以功能堆叠式 AI 平台作为默认叙事，而是围绕售票平台真实场景组织能力：先解决用户咨询与订单问题，再服务运营问数，最后用治理能力保障质量和安全。

## 一、智能客服层

智能客服层是普通用户默认接触的唯一主入口，目标是把高频、低风险、可解释的问题快速闭环。

- 高频问题秒答：优先匹配客服常见问题、购票规则、退改签政策、实名入场、发票和订单状态等稳定知识，减少不必要的模型调用。
- 情绪与升级判断：在用户表达投诉、催单、退款纠纷、黄牛风险或明确要求人工时，优先创建转人工工单，而不是继续让模型反复追问。
- 统一助手兜底：未命中高频问题时，再进入统一助手，由 RAG 检索和业务工具共同生成答案。
- 来源证据展示：客服回答需要展示知识来源、业务工具结果或会话上下文，便于用户和客服运营复核。
- 会话闭环：每次回答都保留会话、运行状态、事件流和反馈数据，为后续评测、知识补齐和问题归因提供依据。

运行时设计上，`run` 是后台执行实体，SSE 只是观察窗口。接口可以创建运行、查询运行、订阅事件，但执行触发应集中在 runtime service 的统一入口，避免控制器和前端感知过多状态分支。

## 二、知识与问数层

知识与问数层服务客服运营和业务运营，默认面向 admin/ops 角色，不应混入普通用户客服入口。

- 知识运营：负责知识文档发布、归档、重建索引、质量报告和统计看板，保证客服答案有稳定、可治理的来源。
- RAG 检索门面：检索入口收敛到统一 facade，底层可以继续保留混合检索、重排和召回策略，但上层不直接散落调用细节，方便统一调参和灰度。
- RAG EvalOps：通过评测集、命中率、引用质量和答案稳定性评估知识库效果，把“答得像不像”变成可量化指标。
- 运营问数：NL2SQL 独立呈现为运营问数能力，适合查询售票转化、库存、订单、退款、场次热度等经营问题。
- 安全边界：NL2SQL 默认只读、带成本守卫；`EXPLAIN` 失败按 fail closed 处理，避免在风险不可估时继续执行 SQL。

这一层的定位是“让客服和运营把知识维护好、把业务问清楚”，而不是额外堆叠一套与客服主线无关的 AI 工具集。

## 三、AI 治理层

AI 治理层服务平台管理员和研发治理，默认不进入普通客服主链路。

- 质量门禁：集中管理答案质量、引用完整性、风险等级和回归评测结果。
- Prompt 治理：沉淀系统提示词、角色边界、拒答策略和灰度版本，避免策略分散在页面或控制器中。
- MCP 边界：MCP resource/prompt/tool 属于治理和扩展能力，应作为 admin/ops 治理能力暴露。
- Red Team：用于压测越权、诱导、注入和幻觉风险，不属于客服日常操作入口。
- 运维证据工作台：RCA 只组装真实 provider 证据，包括日志、指标、Trace、告警、变更、拓扑、Runbook 和业务事件；缺失 provider 时显式降级并要求人工复核。
- 多 Agent / AgentLoop：保留为研发治理能力，除非能证明对售票客服闭环有稳定收益，否则不作为核心入口。

## 管理员治理能力清单

以下能力默认视为管理员治理能力，不应出现在普通用户客服工作台：

- MCP resource/prompt/tool 调试
- Ops Evidence 证据组装与 Runbook 推荐
- DataOps 语义目录、指标宽表重建和 NL2SQL 安全治理
- Red Team 和高级质量门禁压测
- AgentLoop、多 Agent 编排
- 复杂 Prompt 治理控制台

## 设计原则

- 主线优先：任何新能力都要能说明它服务“客服入口 → 回答 → 升级 → 反馈评测”中的哪一环。
- 角色隔离：普通用户只看到客服入口；客服运营看到知识治理；运营/admin 看到问数；研发/admin 看到治理工作台。
- 破坏性收敛：废弃接口和弱实现不保留兼容层，前后端统一切到最终版 `/assistant/**` 管理端 API。
- 少即是多：保留 `BusinessSkill`、`KnowledgeSkill`、`OpsNl2SqlQuerySkill` 三条成熟主线，避免把项目解释成通用 AI 平台。
- 可解释可回归：回答必须能追溯来源，策略变更必须能通过评测集回归，而不是依赖一次性人工判断。
